\section{Discussion}
\label{sec:discussion}

\paragraph{What the agent uses can be learned, best from complete traces.} On four of the five agents, most of what
tools return is never visibly used, and a projection learned from a handful of runs of the same task removes most
of it on a new run. In these agents the learner needed the final answer: an MCP gateway placed between agent and tools can
\emph{apply} a projection, but learning from what it sees alone misses far more of what the agent uses
(\MissesPooledShareRealCalls{} of held-out calls against \MissesPooledShareRealFull{} with real APIs). The practical
consequence is an architecture: learn offline from full traces, review, apply anywhere. Version 0.3 of the library
adds a second route, not evaluated in Studies 1 and 2: the proxy offers the agent one more tool, through
which the agent hands over its final answer, so that the gateway sees complete traces and can learn and apply the
safe part of a projection on its own. Study 3 measured automatic learning through the function-calling adapter,
not through the proxy; in the hosts checked, the agent did call that tool.

\paragraph{Where usage detection is blind, a projection fails.} The losses we found have one cause: the projection
removes what the detector cannot see. The agent transforms values (timestamps into dates, cents into euros, URLs
into short identifiers, English into Italian), or reads a field only to decide something (an issue title to match
a failure). Safeguards can close known blind spots, and S1 and S2 closed three of the four we found, but the list of
possible transformations is open. The general lesson is that a learned projection is a \emph{proposal}, whose
blind spots are exactly the fields that matter in ways the text does not show.

\paragraph{Identifiers are special.} The most serious failure was not a loss but a fabrication: deprived of an
identifier it was asked to report, an agent invented plausible ones. Identifiers are cheap to keep and costly to
lose, so a projection should never remove them, whatever the usage says.

\paragraph{The recovery path matters.} With \texttt{expand}, a wrong cut can cost one round trip instead of a wrong
answer: in the live runs the agents asked for hidden fields, and the end-to-end cost still fell. It is not a
guarantee: in one billing-support run the agent did not ask for the period end and got a ticket wrong. It works only
when the agent knows what is hidden, which is why the hidden fields are listed, grouped, after every trimmed output,
and only while the original is kept: the library keeps the last 256 originals per proxy and lists at most 25 groups,
summarising the rest.

\paragraph{How to use it.} These results suggest a workflow rather than an automatic switch: record a few runs of a
task with full outputs; generate the telemetry report, which is useful on its own and changes nothing; review the
proposed configuration, a plain list of kept and dropped fields; apply it with identifier protection and
\texttt{expand}; and keep recording, so that a field the agent starts needing shows up in the next report. The
library implements each step, including an MCP proxy that applies a configuration in front of any server without
changes to the agent. Reported savings should also be read against re-serialisation alone, which removes up to \ReserialAi{} of the
real-API outputs and \ReserialAiv{} of the simulated ones without removing anything.

\paragraph{What Study 3 adds.} When the task changed and needed fields the projection removed, the agent recovered
them, wrote them, and ordinary learning kept them from the next run; the two corrections designed for harder
cases, promotion and sampling, were not needed in these runs, and sampling only cost tokens. The agent also found a
route around a removed field that no part of the library sees, another tool, which on an API billed per call has a
price. A text teaching the agent to issue independent calls together did nothing measurable for a model that
already did so, and shortened the runs of one agent of a model that did not: whether it helps depends on the
model and the task, so it stays off by default and the telemetry report suggests it when the traces show calls made
one per turn that did not have to wait. The negative results are as informative. Measured offline on these runs,
specialising projections by argument value gained nothing, cutting rows by position would have removed elements the
agent reuses, and hiding unused tool definitions would gain a modest share of the cost where they are cached, which
a few extra turns would cancel.
